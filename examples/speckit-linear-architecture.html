01

What this system is

The one-paragraph version, then the why.

Teams that practice spec-driven development with spec-kit accumulate a folder of feature specs — one directory per feature, each holding the requirements, the plan, and a checklist of implementation tasks as markdown. Those files are excellent for authoring, but the work inside them is invisible in the tracker the team actually lives in. This system closes that gap. It is a spec-kit extension: install it into a repository, and every feature folder is reflected into Linear — one Project per repository, one Issue per feature, one sub-issue per implementation phase, a checklist per task — and it keeps that reflection current automatically as you work.

Two properties define its character. First, the sync is one-way: your repository is the source of truth and the bridge only ever pushes outward to Linear; it never writes back to your files. Second, it is reconcile-based, not event-based: every run reads the current filesystem state and makes Linear match, rather than replaying a stream of changes. That makes every run idempotent and safely repeatable — running it against unchanged files produces no change in Linear at all.

Core idea

The filesystem is the single source of truth for planned work; Linear is a faithful projection of it. The bridge's whole job is to converge that projection to the files on every run — idempotently, observably, and without ever silently destroying information that only exists on the Linear side.

02

How you use it

The operator's view — what a person actually does — before we open the hood.

The bridge is added to a repository through spec-kit's own extension mechanism, and the only thing you need to bring is a Linear API key. Setup is three moves: add the extension to your repository; run the guided install, which discovers everything else from your key; and seed the workspace once. After that, syncing is automatic — finishing any /speckit-* command refreshes Linear in the same step, and local git hooks keep it current when you switch branches, commit, or merge.

The guided install asks for nothing but the key. From it the install verifies your identity, lists the teams you can see as a numbered menu (auto-picking if there's only one), lists that team's projects with a "create new" option, and writes the resolved binding to a committed config file. You never see or type an internal identifier. Failures are fail-closed with guidance: a missing key, an unseeded workspace, or a missing dependency stops with a clear, copy-pasteable remediation rather than a stack trace or a half-built state.

Design choice — the API key is the only input

An earlier install required you to find and paste Linear's internal identifiers, which its UI never shows. The current install inverts that: bring a key, and everything else is discovered for you.

Technical detail — the install discovery flow

The key is resolved in a fixed precedence — environment variable, then a gitignored .env, then an interactive no-echo prompt; in non-interactive mode the prompt is skipped and the install fails closed. It is then verified with a single identity query, whose result is reused for the operator stamp (no duplicate identity call). Discovery then walks a state machine: verify → list teams → team picker (auto-pick when one) → list that team's projects → project picker (or create) → write config → only then register hooks. The binding is written before any hook step, so an interrupted install leaves nothing half-wired. A backwards-compatible non-interactive path accepts pre-resolved identifiers as flags for CI.

03

Architecture at a glance

A reconcile engine over the filesystem, plus an optional real-time webhook, writing into Linear.

The system is built from two layers that converge on the same Linear state from different angles. Layer D is the reconciler: it reads the repository, computes what Linear should contain, and makes it so. It is what every local trigger runs — spec-kit hooks, git hooks, manual commands. Layer E is a GitHub Action that fires on pull-request events and flips exactly one thing: a feature's workflow state when its PR opens, becomes ready, or merges. The two are independently idempotent — either alone keeps Linear converging; together they give both correctness and real-time speed.

State lives in exactly three inspectable places and nowhere else: the repository's filesystem, Linear itself, and the GitHub Action's per-run environment. There is deliberately no database, no daemon, no background watcher, and — importantly — no local "what Linear last saw" cache. Because the reconciler recomputes everything from the filesystem each time, it needs no such cache, and not having one is exactly what lets a fresh clone reconcile correctly.

04

The data model

How a feature folder maps onto Linear, and the small committed file that binds a repo to its Project.

The load-bearing decision of the whole system is a single mapping: how filesystem concepts become Linear primitives. A repository becomes a Project; each feature spec becomes an Issue inside it; each implementation phase becomes a sub-issue; the tasks within a phase become a read-only checklist. Note the deliberate granularity: a phase of work becomes a sub-issue, but an individual task stays a checklist line — which keeps Linear readable and the dependency graph small.

A feature climbs a fixed, ordered ladder of phases, each inferred from what exists on disk. The order is not just for display: it gives each phase a rank, which the authority model (section 8) uses to tell whether the repository is ahead of or behind Linear.

A single committed file, linear-config.yml, binds the repository to its Linear destination. Because the file is committed, the repository is fully self-describing: clone it, run a sync, and it knows exactly where to write.

Bind by identifier, never by name

Every Linear lookup uses an immutable identifier, never a display name. Names are editable in Linear's UI; a rename would silently break a name-based lookup. The only failure mode is deletion, which surfaces as an explicit error. Secrets live outside this committed file: the API key in a gitignored .env for local use, and a separate repository-secret token for the GitHub Action — neither is ever committed.

Technical detail — the committed binding & the phase ladder

The binding file stores the Project and Team identifiers, the operator identity, and the identifiers of the nine workflow states — all as Linear's internal UUIDs, validated before any sync runs. Those nine phases form the ordered lifecycle, each inferred from which artifacts are present on disk:

05

Components

A small set of single-purpose shell modules, plus the files installed into the consumer repo.

The implementation is a set of POSIX-leaning shell scripts, each with one responsibility, reaching Linear two ways: an authenticated session for interactive use, and a direct API call for the paths that have no session (the one-time seed, the git hooks, the GitHub Action). Both converge on the same reconciler logic.

Technical detail — module responsibilities

Two file sets are installed into the consumer repository: the GitHub Action workflow (Layer E) and local git hooks, which chain onto existing hooks rather than overwriting them.

06

How work flows

Four narratives that cover essentially everything the system does.

Install & seed binds a repository from your key alone. The first reconcile against an existing repo enumerates every feature, infers each phase, and creates the matching Project, Issues, sub-issues, checklists, and comments — already-merged features landing directly in Merged without parading through intermediate phases. Lifecycle auto-sync is the everyday path: a spec-kit command's hook advances the matching Issue, posting each clarification exactly once. PR merge is the real-time path: the Action flips a feature's workflow state within seconds of the PR merging.

Technical detail — convergence & idempotency

Every path routes through one reconcile function, so behaviour is identical whether triggered by a hook, a manual command, or a git hook. Idempotency is observable: a re-run against unchanged files makes zero Linear mutations — no modified-timestamps on labels or relations, no duplicate comments. Editing a single task line changes exactly one line in exactly one sub-issue's checklist and nothing else. The retroactive case (a repo adopted mid-flight) converges each feature directly to its current phase with no transitional flips in the activity log.

07

Identity & idempotency

Why running the bridge twice is safe — and how it recognizes an issue it created before, with no local bookkeeping.

Idempotency rests on giving every Linear object a stable identity the bridge can recompute from the filesystem, so it updates existing objects instead of duplicating them — and crucially, it does this without keeping a local mapping file.

A feature Issue is found by a workspace label scoped to the repository's Project; a phase sub-issue by its parent plus a phase label; comments and relations by deterministic identifiers derived from their source. Nothing is remembered between runs.

No sidecar state — by principle

A mapping sidecar would drift across branches, worktrees, and clones; computing identity from the files themselves is what makes a sync from a fresh clone — or any worktree — correct. It is the same discipline that lets the reconciler need no "last-seen" cache.

Technical detail — the recomputable keys

A feature Issue carries a speckit-spec:NNN label (the feature number, evident from the folder name) and is looked up by that label within the committed Project id; a duplicate race keeps the most-recently-active Issue and archives the rest. A phase sub-issue is keyed by parent + task-phase:N. Comments and blocking relations are created with deterministic identifiers derived from their source, so re-syncing the same clarification or dependency never duplicates it.

08

Authority & safety model

Who wins when the repository and Linear disagree, and what the system promises never to do.

The governing principle is the filesystem is the authority. When the repository and a Linear issue disagree, the repository wins — but the bridge will not regress Linear blindly. Before writing, it asks: is Linear ahead of the repository? If the phase Linear records ranks higher than the phase inferred from disk, that is backward-drift. Moving forward — the normal case — never raises it.

When drift is detected the bridge surfaces it and lets the operator decide — interactively it prompts; non-interactively it proceeds and records a loud warning, unless told to skip. Around this sit four guarantees: one-way only (never writes files, never touches PRs); no destructive deletes; fail-closed setup (an unseeded workspace halts cleanly); and idempotent & observable (an unchanged repo produces zero changes, every run ends with a structured summary).

Surface, don't enforce

Detection is automatic, but resolution belongs to the operator. The bridge makes the risk visible and loud; it does not make the decision for you. That split is what lets "the filesystem wins" be safe to live with on a team.

Technical detail — the two drift signals

Backward-drift is computed from two inputs. The primary, semantic signal is phase ordering: drift fires when Linear's recorded phase rank strictly exceeds the disk-inferred rank — clock-independent, so "Linear says Merged, disk infers Planning" is unambiguous. The corroborating signal is recency: the feature folder's last git-commit time (never file mtime, which doesn't survive clone or checkout) versus Linear's last-updated time, with a small clock-skew tolerance. Recency may reinforce but never raises drift alone — otherwise the bridge's own writes would register as false positives. Forward or equal movement never fires; a no-drift re-run writes nothing.

09

Decisions & evolution

The choices that shaped the system — including the two places the design revised itself.

Evolution — write authority was redefined

The original rule was a hard gate tied to git branches: only a worktree on a feature's own branch could write it; every other worktree was read-only. Real use showed it too strict for the common cases — merged features (branches deleted), retroactive adoption, and teams working on main — where it locked the operator out. It was superseded by the drift-aware model in section 8: any worktree may write, and the bridge detects and surfaces a backward move rather than forbidding it. The reasoning: the filesystem, not the branch name, is the real authority. The body above describes only the current model; this note preserves why it changed.

Evolution — install became key-only

The first install required the operator to bring Linear's internal identifiers up front — values its UI never displays. It was revised so the operator brings only an API key and the install discovers everything else through interactive pickers, never surfacing an identifier. The UUID-first path survives only as a non-interactive option for automation.

Other notable decisions: implement as POSIX-leaning shell (the smallest runtime already on a developer's machine); reconcile from scratch each run with no cache (idempotent, converges from any state); identify issues by a recomputable label (no mapping sidecar to drift); split sync into two layers with disjoint write domains (webhook speed plus reconcile correctness).

Boundaries & open questions

What the system deliberately does not do — and the questions its own specs leave open.

Out of scope by design: no reverse-sync (the flow is one-way — Linear is read to look issues up and to detect drift, but never to update your files), no pull-request mutation, and no destructive deletes (the bridge creates and updates issues; the one removal it performs is archiving a duplicate Issue from a rare race; a checklist ticked in Linear is rewritten on the next reconcile, and a banner says so). The following are genuinely unresolved in the specs — recorded, unanswered, rather than guessed at.

Known gap — merged features on a deleted branch

When a feature's PR has merged and its branch is deleted, the bridge can struggle to detect the merge from a different worktree, leaving the feature at an earlier phase. Writing from any branch lets the correct state be written, but reliably inferring "merged" without a live branch reference is flagged as a separate hardening still to be done.

Unspecified — orphaned phase sub-issues

If an entire implementation phase is removed from tasks.md, what becomes of the sub-issue it created is not specified at all — neither cleanup nor retention is defined. The specs leave this open.

Unspecified — API limits & large content

The bridge's defence against partial failure is general re-runnability — an interrupted sync converges on the next run rather than handling Linear's rate limits specifically. Any ceiling on Linear description size is unspecified. And the team/project pickers show only the first page — pagination of long lists is explicitly deferred.

Where this is headed

The one forward-looking idea that is structural rather than speculative.

One forward-looking idea is structural rather than speculative. The system already keeps a deliberate separation between the half that reads the repository and the half that talks to Linear, with a tool-agnostic model of "the work" in between. That seam is what makes a second destination — a different tracker, or a synthesized architecture document — a matter of adding a writer against the same internal model, rather than a rewrite. Linear is simply the first destination proven against it; the structure is built so it need not be the last.

Unspecified — the broader roadmap

The "lift the engine out into a shared, vendor-neutral format" ambition lives in the project's wider planning, not in these feature specs. What the specs themselves support is the narrower, verifiable claim above: a clean internal seam that a future destination could reuse.
