01 — The picture in one read

What this system is

The one-paragraph version, then the why.

This system is a spec-kit extension: install it into a repository, and every feature folder is reflected into Linear — one Project per repository, one Issue per feature, one sub-issue per implementation phase — and it keeps that reflection current automatically as you work.

Core ideaThe filesystem is the single source of truth for planned work; Linear is a faithful projection of it. The bridge converges that projection to the files on every run — idempotently and without silently destroying information.

02

Architecture at a glance

A reconcile engine over the filesystem, writing into Linear.

The reconciler reads the repository, computes what Linear should contain, and makes it so. It is what every local trigger runs.

Technical detail+

State lives in exactly three inspectable places: the repository's filesystem, Linear itself, and the GitHub Action's per-run environment. There is no database, no daemon, and no local "last-seen" cache — the reconciler recomputes everything from the filesystem each run.

04

Authority & safety model

Who wins when the repository and Linear disagree.

The governing principle is that the filesystem is the authority. When the repository and a Linear issue disagree, the repository wins — but the bridge will not regress Linear blindly.

Evolution — write authority was redefinedThe original rule was a hard gate tied to git branches: only a worktree on a feature's own branch could write it. It was superseded by the drift-aware model: any worktree may write, and the bridge detects and surfaces a backward move rather than forbidding it.
Unspecified — orphaned phase sub-issuesIf an entire implementation phase is removed from tasks.md, what becomes of the sub-issue it created is not specified at all — neither cleanup nor retention is defined.
Technical detail+

Backward-drift fires when Linear's recorded phase rank strictly exceeds the disk-inferred rank — clock-independent. A corroborating recency signal uses the feature folder's last git-commit time, never file mtime, with a small clock-skew tolerance.
