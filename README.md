# spec-kit-synthesis

Turn a project's scattered **spec-kit specs** into one readable, beautiful,
interactive **whole-system architecture storybook** (HTML).

Not a dashboard, not a per-spec renderer. It *synthesizes*: it reads many
overlapping, evolving, sometimes-contradictory feature specs and reasons them
into a single **current-state** architecture narrative — organized by structure
(data model, components, flows, safety model), not by spec history. Spec numbers
never appear in the prose; they live only in drill-down citations.

A newcomer reads one generated document and understands how the whole system is
built — accurately, in plain English, with every claim traceable to a source.

## What it produces

A self-contained interactive HTML document with:

- **Three reading depths** in one page (a "Read as: Overview / Technical /
  Sources" control): plain-English for an executive (Layer 0), engineering
  detail for a developer (Layer 1), and named source-typed citations (Layer 2).
- **Hand-rendered, theme-aware SVG diagrams** (pipeline, mapping, lifecycle
  ladder, decision flow), light/dark theme, scrollspy TOC.
- **Honest gaps**: where the specs leave something open — or contradict each
  other — the document says so (an "Unspecified" callout) rather than inventing
  an answer.

See `examples/`:
- `speckit-linear-architecture.html` — the hand-written **north-star** target.
- `generated/speckit-linear-architecture.generated.html` — the same system,
  **generated by this tool**, plus `generated/RESULT.md` (the run record and the
  faithfulness-review convergence).

## How it works

The LLM is the engine, not a helper: this is a **skill**, and the in-session
Claude Code agent does the reasoning. Deterministic `uv` scripts (no LLM inside)
hold the parsing, the fail-closed faithfulness gate, and the renderer.

```
specs/ ─ adapt ─▶ fragment corpus ─ extract ─▶ digests ─ reconcile ─▶ architecture model
                  (code)              (agent)             (agent)        │
                                                          compose (agent) ▼
   architecture.html ◀─ render ◀─ verify (fail-closed) ◀─ document model
        (code)                       (code)
```

- **adapt / verify / render** are deterministic code.
- **extract / reconcile / compose** are the agent's reasoning, following
  `skill/SKILL.md`.
- **Faithfulness is code-enforced**: `verify.py` rejects any claim whose
  provenance doesn't resolve, any ungrounded block, any empty callout, or a
  missing coverage note — exit non-zero, fail closed. A confident wrong doc is
  worse than none.

## Usage

Toolchain is [`uv`](https://docs.astral.sh/uv/) (not `pip`).

```bash
# Stage 0 — adapt the specs and get the agent's hand-off brief:
uv run python skill/scripts/synthesize.py path/to/specs --work .synthesis \
    --project-name "My System"

# … the in-session agent then reasons the architecture (see SKILL.md),
#   writing .synthesis/architecture_model.json + document_model.json …

# Finish — verify (fail-closed) and render, in one command:
uv run python skill/scripts/synthesize.py path/to/specs --work .synthesis \
    --out architecture.html [--theme theme.json]
```

Individual stages are also runnable directly (`adapter_speckit.py`,
`verify.py`, `render.py`); `synthesize.py` orchestrates them.

## Repository layout

```
skill/
  SKILL.md                  the orchestration algorithm (the agent's instructions)
  scripts/
    schema.py               the IR contracts (source-typed provenance, altitudes)
    adapter_speckit.py      specs → source-typed fragment corpus
    verify.py               fail-closed faithfulness gate
    render.py               document model + theme → interactive SVG HTML
    synthesize.py           the one-command front door
  tests/                    51 unit tests (uv run pytest)
examples/                   the north-star target + a generated result
DESIGN.md                   the full design rationale (read §11 for the resolved architecture)
```

## Continuous integration

CI (GitHub Actions, `.github/workflows/ci.yml`) runs the test suite on
Python 3.11 and 3.12 for every push and pull request. The convention is to
**run the exact CI command locally before pushing**:

```bash
uv run pytest skill/tests -q
```

That is the same command CI runs (after `uv sync --dev`). If it passes
locally, it passes in CI.

## Usage at a glance

```bash
# Specs only → architecture storybook:
uv run python skill/scripts/synthesize.py path/to/specs --work .synthesis \
    --project-name "My System"
#   … the in-session agent reasons the IR (it cites only .synthesis/locators.txt) …
uv run python skill/scripts/synthesize.py path/to/specs --work .synthesis \
    --out architecture.html

# Specs + code → adds the coverage view (specified vs built):
uv run python skill/scripts/synthesize.py path/to/specs --code path/to/src \
    --work .synthesis --out architecture.html
```

## Status

**Phases 1 and 2 complete and proven**, each judged faithful (0/0/0) by an
independent cross-model review (`examples/generated/`):

- **Phase 1 — the synthesis engine.** spec-kit specs → one current-state
  storybook; supersessions collapsed to evolution notes; gaps surfaced as
  "Unspecified". (`speckit-linear-architecture.generated.html` + `RESULT.md`.)
- **Phase 2 — code as a second source / the coverage view.** A code adapter
  feeds the *same* source-agnostic core (the seam held — zero core changes), so
  the storybook can cross-check the specified architecture against the actual
  code and show, per area, what is specified-and-built vs specified-but-not-in-
  the-scanned-source. (`speckit-linear-coverage.generated.html`.)

adapters (design-doc/ADR); host-theme detection.
